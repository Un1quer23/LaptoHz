# 下个版本更新方向研究

研究日期：2026-10-05。研究基线：当时的工作区及交付程序 **0.3.0-beta.4**。下文保留当时的建议与证据。

2026-10-06 落实范围：**0.3.0-beta.5 仅实现 4.1 的恢复结果校验**，新增实际后端流程的注入回归并完成交付验证；详见 [验证记录](../VALIDATION.md)。托盘诊断入口、诊断字段扩展及其他日常场景验收继续作为后续候选，未计入本版完成项。

建议下一版 **0.3.0-beta.5 聚焦切换失败后的恢复验证、托盘诊断入口和真实使用场景验收**；达到验收条件后发布 0.3.0 正式版。随后用 0.4.0 增加临时手动和可选全局快捷键。这个顺序能把现有的物理档位筛选、三种模式和结果校验变成更容易信任、遇到问题也容易排查的产品。

判断依据是源码、已有测试与适配记录、本次只读诊断，以及微软文档和少量竞品官方资料。没有用户使用统计，优先级是对当前项目的产品判断，不代表已经证实的市场需求。

## 1. 当前基础与实际缺口

| 项目 | 当前证据 | 对更新方向的影响 |
|---|---|---|
| 核心使用流程 | 自动／确认／手动、插电／电池目标、模式记忆、自启、中文托盘、主题跟随均已实现 | 下一版可以围绕现有流程完善，不需要再造模式体系 |

## 3. 候选方向排序

P0 表示正式版发布前优先完成，P1 表示下一测试版的主要产品更新，P2 表示随后一版，P3 表示先收集需求或做验证。工作量为相对判断，不是工期承诺。

| 优先级 | 方向 | 直接收益 | 相对工作量 | 建议位置 |
|---|---|---|---|---|
| P0 | 恢复后的回读验证与明确结果 | 失败之后知道最终停在哪个状态 | 中 | beta.5 |
| P0 | 真实电源／恢复／登录／多屏验收 | 确认日常工作流和支持范围 | 中，部分依赖设备与人工操作 | beta.5 至正式版 |
| P1 | 托盘导出诊断、补充环境与最近操作信息 | 其他用户能直接提供可用的排障资料 | 中 | beta.5 |
| P1 | 诊断与帮助入口、详细运行状态 | 从“为什么暂停”走到“下一步怎么处理” | 小至中 | 与诊断入口一起做 |
| P2 | 临时手动，到期回到原来的自动／确认模式 | 临时保留高刷后不必记住恢复规则 | 中 | 0.4.0 |
| P2 | 可选全局组合快捷键 | 减少频繁打开托盘的操作 | 中 | 0.4.0 |
| P2 | 统一发布脚本与版本检查 | 减少 EXE、资源、清单和压缩包版本不一致 | 小至中 | 正式版交付准备 |
| P3 | 通知偏好 | 让不同用户选择提示时长和成功提示频率 | 小至中 | 有明确需求后；默认保持现有 9 秒 |
| P3 | 按应用／系统节能状态的规则 | 对特定使用场景增加自动化 | 大 | 先做可行性验证与交互设计 |
| 暂缓 | 外接屏控制、复制模式、DRR 接管、厂商 GPU／电源控制、自动更新 | 扩大适用范围或系统控制能力 | 大且增加新的验收范围 | 当前缺口收敛后再单独评估 |

## 4. 建议 beta.5 的具体范围

### 4.1 恢复结果要能单独核实

现有切换成功判定已经读回显示状态。建议失败恢复采用同等清晰的结果表达：

- 恢复前确认原输出、显示能力和会话仍满足条件；发生取消或路径变化时记录未恢复的具体原因。
- 分别记录恢复接口返回码和恢复后的回读结果，区分“未执行”“请求被拒绝”“已请求但未验证”“恢复已验证”。
- 与切换前快照比较原标称／桌面／信号频率及分辨率、色深、方向、排列、缩放、高级颜色状态。分数频率使用已有容差与等效档位规则；原状态存在桌面／信号差异时，以原快照为准。
- 有限次数回读，超时后报告当前可见状态，避免失败后连续来回切档。
- 把请求、校验和恢复结果传到控制器、提示和诊断资料中；不要仅凭布尔字段名称暗示恢复已完成。

验收至少覆盖：恢复接口成功且回读符合原状态、接口成功但回读不符、接口拒绝、输出路径变化、操作被取消、分数频率，以及原快照桌面／信号不同的情况。当前控制器测试的模拟 `Apply` 不能替代真实显示后端的恢复流程测试；需要可控的后端接口或独立的结果判定测试。

这是源码检查发现的验证缺口，尚无“本机实际恢复失败”的复现证据。微软的 [ChangeDisplaySettingsExW 文档](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-changedisplaysettingsexw) 说明接口返回码和 `CDS_TEST` 的含义；本项目对信号和周围参数的核对属于额外的产品保证。

### 4.2 从托盘直接取得诊断资料

把现有“查看诊断日志”扩展为“诊断与帮助”子菜单，建议包含：

1. 查看详细状态：当前 Hz、桌面／信号差异、模式、插电／电池目标、暂停原因和最近一次操作结果。
2. 导出诊断报告：选保存位置，保存 JSON 和简短可读说明；默认不附加日志，日志可作为可选附件。
3. 查看诊断日志：复用已有实际路径定位修复。
4. 打开 Windows 显示设置：附“显示 → 高级显示”的短指引，帮助处理 DRR 或检查系统报告。

报告在保留旧字段的基础上增加格式版本、采集时间、Windows 构建号、与输出路径关联的显卡／驱动信息、当前有效模式、运行中与已保存的设置差异、暂停原因代码，以及最近请求／验证／恢复的结果与耗时。读取不到的字段明确为空或未知，不能用 GPU 名称推测驱动版本。

导出时使用显式的只读任务，复用显示快照与 JSON 生成，不触发自动切换、自启注册或模式变更。运行实例的未保存选择与磁盘配置应分别表示：现有独立 `--diagnose` 读取磁盘设置，不能直接代表运行实例的全部状态。硬件采集时间与最近操作时间也应分别记录。

保留本地保存、无序列号的原则；默认可读摘要不带用户名或本地路径。原始日志附件需明确包含本地排障信息。导出失败、权限不足、取消保存、非 ASCII 路径和显示能力刚好变化都应有可理解的结果。

微软当前 [设置 URI 文档](https://learn.microsoft.com/en-us/windows/apps/develop/launch/launch-settings) 注明，在 Windows 11 上 `ms-settings:display-advanced` 打开的是显示设置页。按钮宜称“打开显示设置”，不承诺所有系统构建都直达高级显示。

### 4.3 补齐日常场景验收

| 场景 | 核对结果 |
|---|---|
| 自动模式真实拔电／插电、快速重复插拔 | 最终供电目标正确，过期任务不执行，重复通知不反复切档 |
| 确认模式确认／保持／关闭、建议期间再次插拔 | 只执行当前有效建议；保持与关闭保留确认模式 |
| 手动模式插拔、睡眠与应用重启 | 不自动覆盖选档；重启不重应用上次手动 Hz |
| 睡眠期间换电源、锁屏与息屏恢复 | 自动核对正确；确认模式按实际变化补问；不可交互期间不弹干扰窗口 |
| 真正注销／重登或重启 | 已开启的自启运行；已关闭或被 Windows 禁用的选择被尊重 |
| 外接扩展屏、仅外屏后恢复、外屏设为主屏 | 仍只处理内屏，外屏参数保持；内屏恢复后流程正确 |
| 复制模式、DRR、远程／非活动会话 | 不提交切换；说明原因；状态解除后模式语义正确 |
| 100%／150%／200% DPI、混合 DPI、高对比度、窄工作区 | 菜单和弹窗可完整操作，定位正确，不抢焦点 |
| 支持 HDR／旋转／GPU 输出路径切换的设备 | 周围显示参数保持，旧能力和旧确认请求失效 |

每项分开记“通过／失败／未测／设备不支持”，保留版本、环境和失败详情。稳定版的最低要求是主力机日常关键流程完成真实验收，最终构建回归通过，并明确公布仍待测范围。若对外主打通用适配，建议再收集至少两种不同显示输出路线的 Windows 11 笔记本记录，例如 AMD 核显直连与另一 Intel／NVIDIA 路线；两台新设备只是扩展样本，不足以证明普遍兼容。

## 5. 0.4.0 最值得增加的日常功能

### 临时手动

场景：原本自动切换，电池下临时需要高刷，过一段时间希望恢复原来的管理方式。

建议增加可选“临时手动”，时长可先提供 15／30／60 分钟。进入时只暂停规则并保持当前显示；选档仍遵循“先手动、再选刷新率”。菜单显示剩余时间和将恢复的模式，并提供“立即恢复”和“改为持续手动”。

持续手动保持现有语义。临时状态与持久模式分开保存；建议临时状态仅存在本次运行，重启使用原持久模式。到期时返回此前的自动或确认模式：自动模式按当前供电与能力核对；确认模式重新建立当前供电基线。睡眠、锁屏或内屏不可用时延后实际处理，恢复后重新读取状态；不按计时开始时的旧 Hz 强制恢复。用户再次改模式后，旧计时任务失效。

该功能需要处理计时、取消、重启、供电变化与模式关系，工作量高于简单增加一个菜单项。若用户很少忘记恢复规则，可把它放到快捷键之后。

### 可选全局组合快捷键

建议先支持打开菜单／详细状态、选择模式和恢复自动，默认不绑定，由用户主动设置。选档快捷键需要处于手动模式；不隐含改变模式。延续当前菜单的方向键／Enter／Esc 操作约定。

使用 [RegisterHotKey](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-registerhotkey) 和 `WM_HOTKEY` 即可接入现有消息循环。处理已占用组合、配置保存失败、按住重复触发、退出注销，以及目标刚刚不可用的情况；注册失败要显示结果。快捷键只是新入口，仍经过现有忙碌、会话和能力校验。

## 6. 更复杂方向何时值得做

**应用规则：** 先证明用户确实需要按应用切换。第一轮宜只验证指定应用的前台规则：退出或离开后按当前供电重新解析目标，手动选择优先，并控制快速切换窗口造成的连续黑屏。确认模式增加应用触发会改变目前“实际供电变化才询问”的约定，需先明确交互。Windows 的 [SetWinEventHook](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwineventhook) 提供进程外事件回调，可作为前台变化研究入口；它本身不能可靠判定所有游戏或播放状态。

**系统节能／低电量规则：** 先定义它与供电目标、应用规则、手动模式的优先级，以及阈值附近的回切行为。当前任务不需要同时接管电源计划、GPU 或 DRR。附加规则应继续解析成一个刷新率目标，交给已有校验流程执行。

**功耗与续航：** 微软说明降低刷新率可能节省电量；本项目尚无本机定量对照。可做固定亮度、显示内容、分辨率、HDR、GPU 路线和后台负载的高低档交叉测量，重复记录平均功耗、波动和工具自身开销。先建立可信结果，再决定是否值得发展更多省电规则；不能从旧版短时空闲 CPU 记录推导当前版本的续航提升。

**发布便利：** 目前版本字符串分布在 CMake、`support.hpp`、资源和清单，正式发布脚本还有保存在被忽略的 build 中的版本。建议把可复用发布流程放进 `scripts`，统一检查版本、包内相对路径与 SHA256，保留升级前后的配置／自启验证。自动更新需要稳定的发布来源与升级恢复设计，可后续单独评估。

## 7. 推荐交付顺序与判定

1. **beta.5：** 恢复结果验证 + 托盘诊断与帮助 + 环境／最近操作信息；完成主力机真实插拔、睡眠、重登等关键验收。范围超出一轮时，先交付恢复验证和诊断导出。
2. **0.3.0 正式版：** 最终交付构建回归、MSVC 构建验证、明确的支持矩阵与升级交付检查；发布范围以实际通过记录为准。
3. **0.4.0：** 临时手动 + 可选组合快捷键，保留现有三模式约定。
4. **后续探索：** 根据其他机型报告、实际使用需求与功耗对照，再决定应用规则、节能规则或外屏管理。

本次产出为更新方向研究和只读诊断资料，没有修改程序实现、设置、自启或刷新率，没有把尚未执行的验收记为通过。
